# 核心链路 QA 面试复盘

这份复盘记录本次核心链路质量保障的实际过程、设计理由、实现要点和验证边界。面试时建议按“业务风险 → 测试设计 → 缺陷证据 → 修复方案 → 回归结果 → 未覆盖风险”来讲，不要只报测试数量。

## 1. 项目背景与目标

这是一个 Flask 校园二手交易项目。本次 QA 聚焦会影响资金、数据所有权和账户安全的链路：

```text
申请邮箱验证码 -> 注册 -> 登录
卖家发布商品 -> 买家选择自己的地址下单 -> 扣减库存 -> 订单 paid
卖家发货 -> 订单 shipped -> 买卖双方查看或发送订单消息
```

我把目标拆成三类：

1. **业务正确性**：库存不能超卖；订单、库存和系统通知不能只写入一部分；订单状态只能按允许的方向迁移。
2. **访问控制**：用户只能操作自己的地址，只有买卖双方能查看订单、聊天和消息。
3. **认证与输入可靠性**：验证码必须匹配邮箱、未过期且不能重放；异常请求应得到明确的失败结果，而不是 500 或意外副作用。

范围是现有接口实际提供的行为。当前模型里虽然有 `completed` 和 `cancelled` 状态，但项目没有完成/取消订单的迁移 API，因此本次不把这两个状态说成已实现或已测试。

## 2. 实施过程与每一步的考量

### 第一步：先画链路、识别高风险点

先梳理用户、商品、地址、订单、验证码和订单消息之间的关系，并阅读对应路由、模型和已有测试，再根据失败后果排优先级。

| 风险 | 为什么优先 | 本次验证重点 |
|---|---|---|
| 并发下单 | 一件商品被重复卖出会直接造成履约问题 | 两个独立客户端竞争最后一件库存 |
| 订单部分提交 | 库存已扣但订单/通知缺失会导致数据不一致 | 模拟事务提交失败并检查所有持久化结果 |
| 越权访问 | 地址、订单消息和聊天可能包含个人信息 | 买家、卖家、无关第三方分别验证权限 |
| 状态迁移 | 重复发货或非卖家发货会破坏订单语义 | 只允许卖家执行一次 `paid -> shipped` |
| 邮箱验证码 | 错配、过期或重放会削弱注册验证 | 按邮箱、验证码值、创建时间和使用次数设计输入 |

**考量：**先理解业务状态和现有实现，避免只按 URL 罗列“接口通不通”。高风险场景同时关注响应、数据库状态和副作用，这样才能确认不是“返回错误但数据已经被改了”。

### 第二步：用等价类、边界值和状态迁移展开用例

- **等价类**：有效邮箱/无效邮箱、正确验证码/错误验证码、本人地址/他人地址、订单参与方/非参与方。
- **边界值**：空字段、零或非整数 ID、恰好一件库存、验证码刚过期/未来时间、空白消息。
- **状态迁移**：订单从 `paid` 发货后成为 `shipped`；买家不能发货，已发货订单不能再次发货。
- **并发场景**：不是把同一个请求串行执行两次，而是让两个独立 HTTP 会话并发竞争同一份库存。
- **失败路径**：在提交阶段注入异常，然后检查库存、订单和通知是否共同回滚。

这样设计是为了让每个用例都对应一个明确的业务不变量。例如“库存不可小于零”不能只检查 HTTP 状态码，还要检查最后的库存和订单数。

### 第三步：搭建隔离、可重复的自动化环境

实现位置：

- `tests/conftest.py`：启动真实的本机 Werkzeug HTTP 服务，提供 `requests.Session` 客户端 fixture。
- 根目录 `conftest.py`：设置测试配置、临时 SQLite 文件数据库，并在每个测试前清理数据。
- `pytest.ini`：注册 `api`、`order`、`security`、`email_code` 等 marker。

设计理由：

1. 用 `requests` 通过 HTTP 调用，而不是只直接调用 Flask view 函数，可以覆盖路由、请求解析、session cookie、认证装饰器和响应序列化等集成行为。
2. 每个测试用独立 session，避免登录 cookie 在用例间串用；每个测试前清数据，降低执行顺序依赖。
3. 测试数据库放在独立的系统临时目录，避免访问开发用 MySQL，也让测试结束后可清理。
4. 并发测试用 SQLite **文件数据库**而不是内存数据库，让不同线程/连接访问同一份持久化测试数据。
5. 邮件发送用 `unittest.mock.patch` 替代真实 SMTP，测试可以确认“是否发送、发送失败后是否写验证码”，又不会真的外发邮件。
6. 测试 HTTP server 在 Windows 上从一段明确端口范围内挑选可用端口，避免随机端口恰好撞上 Windows 客户端临时端口范围。

**CI 首次运行发现的环境问题：**根目录 `conftest.py` 原先先导入 `app`，而 `app.py` 在模块导入时就根据 `config.py` 初始化 SQLAlchemy。GitHub Linux runner 没有安装 MySQL 驱动，因此在 pytest fixture 还没来得及把数据库切到 SQLite 前，就因缺少 `MySQLdb` 而导入失败。修复后，测试入口先创建唯一的临时 SQLite 文件路径，并通过 `SQLALCHEMY_DATABASE_URI` 环境变量在导入 `app` 之前设置数据库 URI；`config.py` 支持该环境变量覆盖默认 MySQL URI。应用初始化后，fixture 还会检查实际 SQLAlchemy engine 后端必须是 SQLite，不符合就立即失败，避免测试意外连接开发数据库。生产环境没有设置该变量时仍使用项目默认数据库配置。

**测试边界：**`create_app('testing')` 提供测试配置入口，但当前仍复用模块级 Flask app，不是完全隔离的多实例应用工厂。更成熟的长期改造是把扩展初始化和路由注册迁入真正的 `create_app`，让测试和生产实例完全分离。

### 第四步：覆盖认证与邮箱验证码

实现和测试关注点：

- 登录兼容现有网页表单重定向，同时支持 JSON 客户端使用 `Accept: application/json` 或 JSON 请求体取得结构化结果。
- 注册验证邮箱基本格式、密码和验证码是否提供，并检查邮箱是否已注册。
- 只接受与邮箱匹配、未超过 30 分钟且创建时间不在未来的验证码。
- 注册成功时，在同一数据库事务里新增用户并删除验证码，随后再提交。
- 邮箱验证码接口先校验邮箱，再生成 6 位数字验证码；只有邮件发送成功后才保存验证码。
- 用参数化测试覆盖错误输入；用 mock 验证无效邮箱不会发送邮件、发送失败不会保存验证码。

**为什么验证码要一次性消费：**如果成功注册后仍保留验证码，它就可能在有效期内被重放。将用户创建和验证码删除放在同一事务里，可以避免只创建用户或只消费验证码的部分成功。

**为什么要校验未来时间：**数据库时间被错误写入未来时，单纯判断“当前时间减创建时间是否大于 TTL”会得到负数，并错误地把验证码判为有效。因此有效时间区间应同时满足 `created_at <= now` 和 `now - created_at <= TTL`。

### 第五步：修复下单并发与事务一致性

旧的思路是先读取 `product.num`，然后在 Python 中做 `product.num -= 1`。这存在典型的 **check-then-act** 竞态：

```text
请求 A 读取库存 = 1
请求 B 读取库存 = 1
请求 A 扣减并创建订单
请求 B 也扣减并创建订单
```

修复后在数据库执行带条件的原子更新，核心条件是商品 ID 匹配、库存大于零、商品所有者不是当前买家：

```python
update(Product).where(
    Product.id == product.id,
    Product.num > 0,
    Product.publisher_id != g.user.id,
).values(num=Product.num - 1)
```

再检查受影响行数：为 1 表示成功占到库存；为 0 表示条件不成立，按库存不足处理。数据库对单条 `UPDATE` 做原子执行，使两个并发事务不能都成功消费同一件库存。

随后把库存扣减、订单写入、系统通知写入放到同一个事务中：先 `flush()` 取得新订单 ID、再创建关联消息，最后只 `commit()` 一次。任何异常都执行 `rollback()`。

**考量：**

- 条件更新把“检查库存”和“扣减库存”合并到数据库的一条操作中，避免应用层读写之间的竞态窗口。
- 一个事务保证库存、订单、消息要么一起提交，要么一起回滚。
- 测试使用两个 `requests.Session` 和 `ThreadPoolExecutor` 同时下单，并检查结果为一个成功、一个失败，库存为零且订单/系统消息各只有一份。
- 另一个用例 mock `commit()` 产生异常，断言库存恢复、订单不存在、消息不存在，验证失败路径而非只验证成功路径。

**重要边界：**SQLite 上的并发回归证明了测试数据库中该实现的行为，但不能替代目标 MySQL 版本、隔离级别、锁等待和连接池条件下的并发压测。上线前应在目标数据库验证，并关注锁冲突、死锁重试和请求幂等性。

### 第六步：验证订单状态迁移和越权边界

- 发货操作除检查卖家身份外，还使用带 `order_id`、`seller_id`、`status == PAID` 条件的更新，将状态迁移限制在 `paid -> shipped`。
- 受影响行数不是 1 时，认为状态已变化或迁移条件不成立，不再重复发送发货通知。
- 地址更新、删除、设为默认均检查地址 `user_id` 是否等于当前登录用户。
- 下单时校验地址归属当前买家，阻止用他人地址下单；也拒绝购买自己的商品。
- 订单消息 API 和聊天页面分别检查当前用户是否为买家或卖家。页面路由也要做授权检查，不能只保护背后的 JSON API。
- 订单列表按当前用户对应的 `buyer_id` 或 `seller_id` 查询，不允许客户端通过参数读取其他人的订单。

**面试可强调：**认证（Authentication）回答“你是谁”；授权（Authorization）回答“你能对这个资源做什么”。`@login_required` 只能证明用户已经登录，仍必须做对象级授权，即校验订单参与者或地址所有者。

### 第七步：补足请求体校验并锁定回归行为

- 下单和订单消息使用安全读取 JSON 的方式，先判断 body 是否为字典，再验证字段类型、缺失值和空白字符串。
- `bool` 是 Python `int` 的子类，所以商品 ID 检查额外排除布尔值，避免 `True` 被误当成 ID `1`。
- 对无效输入返回明确的 4xx，不让 `None.get(...)` 或非字符串 `.strip()` 变成 500。
- 每修复一个缺陷，都补对应的回归用例，确保问题不会在后续修改中再次出现。

旧版注册/登录接口是网页场景，有既有响应约定，所以部分失败通过 JSON 的 `result: false` 返回、HTTP 状态仍为 200；下单等 API 输入错误则使用 400。面试时要说明这是兼容当前接口约定的实现，不应把 HTTP 200 说成推荐的 REST API 错误码设计。

### 第八步：接入持续集成并形成可交付记录

#### 工作流放在哪里、什么时候触发

GitHub Actions 通过仓库根目录下的 `.github/workflows/tests.yml` 发现工作流。该文件监听三类事件：

1. **push** 到 `main` 或 `master`：分支有新提交时运行。
2. **pull_request** 目标分支为 `main` 或 `master`：PR 创建/更新时运行，供合并前回归。
3. **workflow_dispatch**：允许在 GitHub Actions 页面手动启动，便于需要时主动重跑。

这个触发设计让测试覆盖日常提交和合并门禁场景，同时保留人工重跑入口。当前 workflow 不会在任意 feature 分支的普通 push 上触发，除非该分支通过面向 `main`/`master` 的 PR 运行。

#### Job 的具体执行顺序

`tests.yml` 定义一个名为 `pytest` 的 job，运行在 GitHub 托管的 `ubuntu-latest` runner。步骤顺序如下：

1. `actions/checkout@v4` 把当前提交检出到 runner，后面的命令才能读取项目源码和测试。
2. `actions/setup-python@v5` 安装 Python `3.10`；启用 pip 缓存，并用 `requirements-test.txt` 作为缓存键依据，依赖清单变化时避免复用不匹配的旧缓存。
3. `python -m pip install -r requirements-test.txt` 安装 Flask 应用测试需要的包，包括 Flask/SQLAlchemy、pytest 和 requests。
4. `python -m pytest -q` 运行完整测试集。pytest 返回非零退出码时，该 step 和 job 会失败，GitHub 会显示红色检查结果；全部通过则显示成功状态。

对应配置的核心内容如下（与仓库 workflow 保持一致）：

```yaml
name: tests

on:
  push:
    branches: [main, master]
  pull_request:
    branches: [main, master]
  workflow_dispatch:

permissions:
  contents: read

jobs:
  pytest:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.10'
          cache: pip
          cache-dependency-path: requirements-test.txt
      - name: Install test dependencies
        run: python -m pip install -r requirements-test.txt
      - name: Run API and unit tests
        run: python -m pytest -q
```

#### 为什么这样配置

- **只授予 `contents: read`**：job 只需检出代码并读文件，不需要写仓库内容，遵循最小权限原则。
- **依赖单独列入 `requirements-test.txt`**：让 CI 安装命令明确、可复现，也避免为了跑测试而安装与测试无关的开发工具。
- **在依赖清单变化时更新 pip 缓存键**：减少重复下载，同时不把依赖清单变更后的 job 错误地绑定到旧缓存。
- **CI 执行同一条 pytest 命令**：本地和 CI 至少共享相同测试入口，减少“本地通过但 CI 执行了另一套测试”的配置分叉。
- **临时 SQLite + mock SMTP**：CI 不需要生产 MySQL、邮件账号或真实外部服务凭证；测试不会误连开发数据库或发送真实邮件。
- **将测试目录从 `.gitignore` 中移除**：测试文件必须提交到仓库，远端 runner 才能检出并执行它们。

#### 如何验证与当前结论

首次远端运行确认 workflow 能触发并安装依赖，但 pytest 在导入阶段失败，暴露出测试数据库配置晚于应用初始化的问题；按上面方式改为导入应用前注入临时 SQLite URI 后，本地在 Conda `flask-env` 中重新运行 `python -m pytest -q`，47 个参数化展开用例通过。将此修复推送后，还需要查看新 Actions run 的最终状态，才能确认远端回归成功。

另外，当前 workflow 会运行同一套完整测试，但**尚未配置 GitHub branch protection 来强制要求该检查通过后才能合并**。如果要把它做成真正的合并门禁，需要在仓库设置中启用 branch protection/ruleset，并将对应的 `pytest` check 设为 required status check。

#### CI 部分的面试回答示例

> 我把 workflow 放在 `.github/workflows/tests.yml`，监听 main/master 的 push、面向这两个分支的 PR，以及手动触发。runner 使用 Ubuntu 和 Python 3.10，先 checkout 代码、按 `requirements-test.txt` 安装依赖，再运行 `python -m pytest -q`。第一次远端运行暴露了测试 fixture 配置 SQLite 太晚的问题：应用模块导入时已经按默认 MySQL 配置初始化 SQLAlchemy。之后我让测试入口在导入应用前设置临时 SQLite URI，并增加 engine 后端保护，确保 CI 不需要 MySQL 驱动或生产数据库。本地 47 条参数化展开用例通过；修复提交后的远端状态应以对应 Actions run 为准，而且仓库尚未配置 branch protection，所以不把它描述成强制合并门禁。

此外，README 加入本地测试命令，`docs/qa/` 保存测试计划、用例集、缺陷报告、测试总结和面试复盘。


- 9 个认证相关用例（包含参数化展开）。

数量口径要讲清楚：**47 是 pytest 参数化展开后的执行用例数**，不是 47 个测试函数或 47 个完全不同的业务需求。

## 4. 可直接用于面试的项目介绍

### 约 30 秒版本

> 我在这个 Flask 校园二手交易项目里负责核心交易链路的质量保障，围绕注册验证码、下单、库存竞争、发货状态和资源越权设计接口测试。我使用 pytest 管理测试数据和清理，用 requests 通过真实 HTTP 服务做集成测试；邮件通过 mock 隔离，数据库使用临时 SQLite。测试暴露并推动修复了库存并发扣减、订单事务部分提交、聊天页面对象级授权和验证码重放等问题。最终本地 47 条参数化展开用例全部通过，并添加了 GitHub Actions 工作流；远端 Actions 尚未实际触发，MySQL 并发压测也列为上线前工作。

### 约 2 分钟版本

> 我先从业务链路和数据关系入手，确定库存、订单状态和对象权限是最高风险点，而不是只按接口清单做 happy path。测试设计上结合等价类、边界值、状态迁移和并发场景。例如验证码覆盖邮箱不匹配、错误、过期、未来时间和重复使用；地址/订单资源分别以所有者、参与方和第三方身份验证。
>
> 下单并发方面，我发现“先查库存、再在 Python 中减一”存在 check-then-act 竞态，所以将库存扣减改成带库存大于零条件的原子 SQL 更新，并检查受影响行数。同时把扣库存、写订单和系统消息放进一个事务，通过并发请求和提交失败注入分别验证不超卖与整体回滚。越权方面，除了 API，还检查聊天页面本身的订单参与者权限，避免只保护接口却泄露页面入口。
>

## 5. 面试官可能追问

### Q1：为什么不先查询库存，再扣减？

两个并发请求可能都读到库存为 1，然后各自认为可以下单。把条件判断和库存减一放在同一条数据库更新语句里，再根据受影响行数判断成功与否，可以消除应用层读写之间的竞态窗口。

### Q2：为什么订单、库存和消息需要同一事务？

它们共同表达一次下单的业务事实。若只扣库存或只创建订单，会产生无法履约或库存丢失的不一致。事务让这些数据库写入具备原子性：全部提交或全部回滚。

### Q3：如何证明并发测试真的并发？

通过两个独立的 `requests.Session` 建立不同 cookie/login 状态，再由 `ThreadPoolExecutor(max_workers=2)` 并发提交最后一件商品的订单。断言响应状态为一个 200、一个 400，并再次读取数据库检查库存为 0、订单为 1。它是功能性竞态回归，不是高负载性能压测。

### Q4：为什么使用 SQLite？它能代表 MySQL 吗？

SQLite 临时文件库容易隔离、无需触碰开发数据库，也支持本次本地集成测试。它不等价于 MySQL 的锁、隔离级别和连接池行为，因此 MySQL 并发压测仍是上线前验证项；面试时应明确这一点。

### Q5：`login_required` 为什么不够？

它只拦截匿名用户，不保证已登录用户就是资源所有者或订单参与者。对象级授权还要比较当前用户 ID 与地址所有者、订单 buyer/seller ID；页面路由和 API 都要覆盖。

### Q6：验证码为什么需要消费？事务又有什么用？

验证码验证成功后如果不删除，就可能在有效期内重复注册或被重放。用户写入和验证码删除放在一个事务中，可以避免只有其中一项成功。还要校验验证码与邮箱一致、有效期内且创建时间不是未来。

### Q7：为什么用 mock 邮件，而不真的发邮件？

测试目标是验证应用是否调用邮件服务、失败时是否正确处理、何时持久化验证码；SMTP 属于外部依赖，真实发送会让测试依赖网络和凭证、速度慢且可能发出真实邮件。mock 让测试安全、稳定、可重复；邮件供应商的真实投递质量应由单独的集成/监控验证。

### Q8：测试结果中的 47 是什么口径？

这是 pytest 参数化展开后的用例执行数。比如一个测试函数用多个输入组合运行，会产生多个独立 case，所以不要说成“写了 47 个测试函数”。

## 6. 诚实说明的限制与下一步

面试时主动说明边界通常比过度承诺更有说服力：

1. **MySQL 并发验证**：在与生产一致的 MySQL 版本、隔离级别和连接池下做并发压测，关注锁等待、死锁、事务重试和吞吐量。
2. **真实 CI 执行**：提交分支或 PR 后观察 Actions 运行，确认依赖安装、测试发现和失败时的状态检查都生效。
3. **订单完整状态机**：先和产品确认取消权限、完成条件、重复请求幂等语义及取消后库存策略，再实现 `completed` / `cancelled` 迁移及用例。
4. **验证码滥用控制**：补充按邮箱/IP 的发送频率限制、验证码尝试次数、旧码作废、统一且不泄露账户存在性的响应，以及必要的审计记录。
5. **测试架构完善**：将当前复用全局 app 的 testing 配置入口改为真正的 Flask application factory；移除 SQLAlchemy `Query.get()` 弃用调用。
6. **可观测性与并发鲁棒性**：用结构化日志代替 `print`，避免向客户端回传底层邮件异常细节，并补充事务失败和数据库锁冲突的告警/重试策略。
